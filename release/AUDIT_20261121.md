## 2. 本轮三项主要修复

### 2.1 分组布局持有 GPU 资源

**根因**：`Folder` 持有 `Tiles`（`shared_ptr<App>`），`App` 持有 `ComPtr<ID2D1Bitmap>`，位图持有 D2D 设备。teardown 只换出了 `g_apps`/`g_tiles`，而 `g_groupPositions`、`g_groupRows`、`g_groupEditSnapshot`、`g_groupEditRows`、`g_groupTransitions`、`g_groupGesture`、`g_closingFolder` 仍在持有分组，导致 `ResetTarget()` 之后整棵设备树仍然存活，每次禁用/更新都泄漏。

**修复**（`ryjs-launchpad.wh.cpp:12273` `ReleaseLauncherResources`）：

- 新增 `g_closingFolder = nullptr;`；
- 新增 `ClearGroupPositions()`（清空四张分组表、手势、过渡、编辑快照）；
- 新增 `std::vector<ArrangementGeometry>().swap(g_arrangementGeometry)`；
- 复用 `CancelGroupPointer()` 清掉 `g_groupHeaderPressed` / `g_groupDropFolder` / `g_groupHeaderDragging`；
- 顺序保持「先释放持有者，再 `ResetTarget()`」，`g_labelCache` / `g_groupTitleRenders` 在此之前清空；
- 顺带把 `LaunchpadMenu` 的三处 format 重置改为先 `LaunchpadMenu::Reset()`，确保菜单的 `frame`/`backdrop`/`staging`/`surface`/节点布局在卸载时一并释放。

**验证**：新增回归用例构造一个被十余处全局同时持有的分组，调用 teardown 后断言 `weak_ptr` 已过期、四张分组表为空、所有指针持有者为空；第二次调用 teardown 不崩溃（见 §5，510 项功能检查中的 4 项）。

### 2.2 设置窗口静态图形资源

**根因**：`g_setWin`（`shared_ptr<SetWindow>`，内含 `ID2D1HwndRenderTarget`、位图目标、17 个 DirectWrite 格式）与 `g_setD2d`/`g_setDw`/`g_setWic` 是普通静态对象。正常卸载时由设置线程在 `WM_NCDESTROY` 与 `SettingsThreadTeardown()` 释放；但 Explorer 退出（注销/重启）时 `Wh_ModUninit` 不会被调用，设置线程已消失，CRT 会在退出线程上、loader lock 内析构这些 COM 对象。

**修复**（`ryjs-launchpad.wh.cpp:7576`）：四个对象加 `[[clang::no_destroy]]`，显式释放责任写进注释：

- 正常卸载：`WM_NCDESTROY` → `g_setWin.reset()` + `Set_ReleaseFactories()`，随后 `SettingsThreadTeardown()` 再兜底一次（幂等）；
- 进程退出：不再运行析构，交给进程终止，避免 loader lock 下的 COM 释放；
- 不存在「既不自动析构也不主动释放」的对象：两条正常路径都有显式释放点。

### 2.3 开始按钮异步回调

**根因**：`ClearStartButtonLatch` 通过 `CoreDispatcher::RunAsync` 排队一个 lambda，lambda 是本映像中的代码；卸载时若队列里还有它，任务栏线程会执行已卸载的代码。

**修复**（新增 `launchpad_lifecycle.h`，`launchpad_start_xaml.h:66`）：

- `g_startLatchPending`（原子计数）：入队前 `+1`，lambda 末尾或 `RunAsync` 抛异常时 `-1`；
- `g_startLatchStopping`（闸门）：在 `Wh_ModBeforeUninit`（钩子仍在）置位，之后不再接受新请求；入队后二次检查闸门，若已关闭则立即回退计数；
- `Wh_ModUninit` 在 join 启动台线程、钩子已移除之后调用 `WaitForStartLatchResets(5000)`，此时计数只减不增；
- 超时兜底：说明分发器已停止响应，用 `GetModuleHandleExW(...PIN)` 保持映像映射，宁可留下一个已卸载逻辑的模组，也不让回调执行未映射代码（会记日志）；
- `g_startButtonElement`（`weak_ref`）在排空后显式置空；
- 事件句柄在 `Wh_ModInit` 创建、排空后关闭，创建失败与 `CreateThread` 失败路径都会释放。

**没有**使用固定延时或睡眠来掩盖竞争；等待有明确的不变量（钩子已移除 + 启动台线程已 join）。

### 2.4 异步回调：计数所有权与竞争证明（最终复核新增）

**所有权模型。** 每个会在本映像中执行代码的单元独立持有一个计数，且只有两种单元：

| 计数 | 谁持有 | 何时释放 | 释放次数 |
| --- | --- | --- | --- |
| U1 调用单元 | `ClearStartButtonLatch` 栈上的 `StartLatchTicket` | 函数返回或栈展开（RAII） | 恰好 1 次 |
| U2 排队单元 | 队列中的 lambda（内部再套一层 RAII `Release`） | lambda 执行完毕；若 `RunAsync` 失败则由 `catch` 释放 | 恰好 1 次 |

`g_startLatchPending` 只由这两类单元的构造/析构增减，没有第三处 `fetch_add`。

**逐场景证明**（对应本轮要求）：

| 场景 | 结果 | 依据 |
| --- | --- | --- |
| 提交成功，随后卸载标记改变 | 无重复递减 | 标记只影响 `if (g_startLatchStopping)` 的返回路径；已提交的 U2 由 lambda 释放，标记变化不会触发第二次释放 |
| 回调已开始执行，提交线程正在检查标记 | 无重复递减 | 回调持有的是**另一次**提交的 U2；本次提交在 `RunAsync` 返回前不会运行自己的 lambda，两个计数互不相干 |
| 回调结束的同时提交线程尝试回退 | 不可能同时发生 | 回退只发生在 `RunAsync` **之前**（`g_startLatchStopping` 复查失败），此时该次提交的 lambda 尚未入队 |
| `RunAsync` 抛异常 | 恰好释放一次 | `throw ⟺ HRESULT 失败 ⟺ 未入队`；`catch` 释放 U2，没有 lambda 会再释放 |
| 卸载时仍有任务排队 | 排空后归零 | `Wh_ModBeforeUninit` 关闸 → Windhawk 移除钩子 → `Wh_ModUninit` join 启动台线程 → 等待计数归零。此后既无钩子可产生调用，也无启动台线程可产生调用 |

**本轮修复的两个真实缺口**（原方案不完整）：

1. **进入函数但尚未入队的线程没有被计数**。原实现先查闸门、再 `fetch_add`，一个钩子线程若正好停在这两步之间，排空可能先看到 0，随后它再自增并立即回退——这段代码在 `FreeLibrary` 之后执行。现在改为**进入即计数**（U1 是函数第一条语句），排空看到的 0 意味着没有任何线程还在这条路径上。
2. **`g_startButtonElement` 是跨线程读写的非原子 `winrt::weak_ref`**（任务栏钩子写、启动台线程在 `HideNow` 读）。现在写入与复制都在 `SRWLOCK` 内完成，`weak_ref::get()`（会进入 XAML）在锁外执行，避免与任务栏线程互锁。

**下溢与提前释放**。`FinishStartLatchReset` 在 `fetch_sub` 前值 ≤ 0 时记日志、归零并唤醒等待者；正常协议不会走到这里，但即使未来改坏也不会变成「排空永远等不到 0」。计数归零后关闭事件句柄；若未排空（进入锁定兜底）则不关闭句柄，避免晚到的回调向已回收的句柄号发信号。

**依赖的引擎契约**：Windhawk 在 `Wh_ModBeforeUninit` 返回后移除该模组的全部钩子，然后才调用 `Wh_ModUninit`（见 `windhawk_api.h` 对 `Wh_SetFunctionHook`/`Wh_ApplyHookOperations` 的说明）。因此排空开始后不会再有新的钩子调用进入。这是所有 Windhawk 模组卸载的前提，不是本模组独有的假设。

### 2.5 模块锁定兜底的触发条件与影响（最终复核新增）

**5 秒超时在什么情况下发生。** 排空只在等一件事：任务栏 UI 线程把已排队的回调跑完。会超时的情形只有三类：

1. 任务栏 UI 线程被占住超过 5 秒（模态界面、调试器断点、shell 的长时间同步操作），回调排在它后面；
2. 分发器接受了回调但之后再没有抽取消息（任务栏窗口已销毁、线程正在退出），而 `RunAsync` 又没有报错；
3. 等待期间系统进入睡眠，唤醒后超时按已过时间计算。

正常路径上回调在下一帧内执行，等待通常 < 20 ms。

**超时后是否必然永久驻留。** 只有 `GetModuleHandleExW(...PIN)` 成功才驻留；失败会记录日志，此时确实存在「回调执行未映射代码」的残余风险，但在 Windhawk 的卸载契约下没有更安全的动作可做。驻留是**进程级**的：Explorer 重启即消失。

**新旧模块是否会共存。** 会，且只在这种情况下发生。旧映像此时已经「逻辑卸载」：钩子被 Windhawk 移除、所有线程已 join、窗口与托盘图标已销毁、图形与设置资源已释放、6 个窗口类已注销、集成互斥量已释放；只剩映像本身和一个排队中的 lambda。新版本加载后：

- 类名按映像基址唯一（菜单类早已如此），不会与新实例冲突；
- 旧 lambda 只操作它捕获的元素和旧映像里的计数器，不触碰新实例的全局；
- 新旧实例不共享互斥量或存储句柄。

代价是**一个模块映像（约 2 MB）加一个事件句柄**驻留到 Explorer 重启。这是有界、可观测（有日志）的资源累积，不是持续增长。

**延迟回调访问的对象是否仍然有效。** lambda 持有 `ToggleButton` 的强引用：任务栏还活着时对象有效（可能已从可视树摘下，调用会抛异常并被吞掉）；任务栏已随进程退出时回调不会再运行。锁定保护的是**我方代码**的映射，这也是唯一能由模组自己保证的部分。

**是否有更合理的方案。** 逐个排除：

| 方案 | 为什么不采用 |
| --- | --- |
| 无限等待 | 任务栏线程若真的卡死，Windhawk 的卸载界面会永久挂起，且没有任何恢复路径 |
| 取消 `IAsyncAction` | `RunAsync` 返回的 action 未文档化保证「取消即不执行处理器」，依赖它等于赌实现细节 |
| 持有模块引用、由回调释放 | 释放后 lambda 还要返回，会跳回已卸载的映像，比泄漏更糟 |
| 让回调不是本映像代码 | 委托必然指向本映像，无法规避 |
| 定时轮询分发器 | 不能在任意线程安全地探测 XAML 分发器的存活 |

结论：在「不能崩溃、不能死锁、不能无限等待」三个约束下，**有界等待 + 失败时锁定**是唯一同时满足的方案；触发概率低、代价有界、行为可观测。本轮只补强了日志与句柄处理，没有改变策略。

## 4. 资源生命周期审计

### 4.1 线程

| 线程 | 创建 | 结束/join | 结论 |

### 4.2 图形与 COM

所有权链：`Folder` → `App` → `ID2D1Bitmap` → `ID2D1Device` → `ID3D11Device`。teardown 顺序：

1. `g_apps` / `g_tiles` / `g_visible` 换出；
2. 所有 `shared_ptr<Folder>` 持有者清空（分组表、手势、过渡、打开/关闭文件夹、拖拽、多选）；
3. `g_labelCache` / `g_groupTitleRenders` 清空（旧设备位图）；
4. `LaunchpadMenu::Reset()`；
5. `g_backdropImage` / `g_panelBlur` 置空；
6. `FreeSurface(g_surface)`；
7. `ResetTarget()`：`tileGlass`、presenter、frame、staging、brush、shadowContext、target、d2dDevice、d3d；
8. `g_dwrite`、`g_d2d` 释放。

设备丢失：`Render()`/`DrawFrame()` 在 `D2DERR_RECREATE_TARGET` 时调用 `ResetTarget()`、清两个缓存、恢复 `g_openFolder`；菜单按 `g_targetGeneration` 丢弃旧设备的位图。设置窗口在 `WM_PAINT` 里通过 `Set_EnsureRt` 重建渲染目标。

- 窗口类：主窗口、背景、分组名、入口编辑、菜单、设置共 6 个，teardown 全部注销；菜单类名按映像基址唯一；

- 动态库：仅 `comctl32`（成对 Load/Free）与 `twinui.pcshell.dll`（故意保持加载以支撑钩子）。

`no_destroy` 共 56 处声明（约 60 个对象），逐一分类：

## 6. 残留风险专项说明（最终复核新增）

### 6.1 设置窗口关闭期间的线程等待

机制：`CloseSettingsWindow` 置 `g_settingsStop` → 向窗口 `WM_CLOSE` → 循环 `PostThreadMessage(WM_QUIT)`，每 100 ms 检查一次线程是否退出，**无超时**。

会不会死等：

- 设置线程只在两类调用上阻塞：字体枚举/图标 WIC 创建（`Settings_Open`）与一次 INI 写入（`Set_Save`）；
- 设置线程没有任何跨线程等待：全部 `SendMessage` 都发往它自己的窗口与子控件（已逐条核对），不会与正在 join 启动台线程的卸载线程形成环；
- 关窗请求早于窗口建成的窗口期由 `g_settingsStop` 覆盖（`Settings_Open` 返回后先查停止位再进消息循环）。

因此实机上的等待通常是几十毫秒。保留无界等待是刻意的：超时后继续 `FreeLibrary` 会让窗口与线程留下野指针，是崩溃而不是延迟。结论：**可接受的延迟，不是缺陷**，本轮不改。

### 6.2 启动台线程阻塞在 MessageBox 时的卸载（实测：不阻塞）

原报告把它列为「卸载会等用户点击」，本轮用独立实验证伪：

- 实验：创建属主窗口 W，另起线程 400 ms 后 `PostMessage(W, WM_APP_QUIT)`；主线程调用 `MessageBoxW(W, ...)`；W 的窗口过程在收到消息时 `DestroyWindow`。
- 结果：`MessageBoxW` 在 406 ms 返回（结果 0）。属主销毁时其拥有的消息框被一并销毁，模态循环随即结束。

代码侧核对：全部 30 余处 `MessageBoxW` 都传了 `hwnd`/`owner`/`g_wnd`，没有无属主调用；入口编辑器与分组名对话框都以 `g_wnd` 为属主，`DestroyWindow(g_wnd)` 会级联销毁它们及其消息框。

结论：**不是卸载阻塞点**，已从风险清单移除。保留的前提是「每个消息框必须有属主」——已在代码中核对，后续新增消息框时不要传 `nullptr`。

### 6.3 备份任务运行期间的卸载

`StopFullBackupJob` 在 teardown 中等待备份进程与等待线程，无超时。作业本身没有固定上限：导出要压缩并计算每个文件的哈希，导入要先校验再替换。

评估：

- 不是死锁：等待的是外部进程，进程结束即返回；期间不持有任何锁，也不阻塞启动台线程（已 join）；
- 强制终止的风险更大：导入中途被杀会留下半个 `data-v1`（虽有 `.before-import-*` 可回滚），导出被杀会在用户选的目录留下 `.pending-*` 残片；
- 典型存储（几 MB 到几十 MB）耗时数秒，且是用户主动发起的操作。

结论：保留等待，记为**已知的卸载延迟**，不是缺陷。若将来要改，正确做法是让导入脚本支持「接受取消并在检查点回滚」，而不是在卸载路径上 `TerminateProcess`。

### 6.4 提前加载 twinui.pcshell.dll

`Wh_ModInit` 用 `LoadLibraryExW(..., LOAD_LIBRARY_SEARCH_SYSTEM32)` 提前加载 `twinui.pcshell.dll`，以解析 `XamlLauncher::ShowStartView`。`win81-start-screen-recreation` 记录过这种早加载会干扰 StartAllBack/ExplorerPatcher。

不改的理由：改成「等 Windows 自己加载」需要把符号解析搬进模块加载钩子，并保证在 Start 第一次被按下前完成；这条路径只能在装有 StartAllBack/ExplorerPatcher 的实机上验证，当前环境不具备。贸然改会直接改变开始菜单接管的时序，风险高于收益。

结论：保留现状，列为**必须实机验证**的兼容性项。

### 6.5 任务栏线程卡死时的跨线程消息

`StartButtonHooksStop` 会用 `SendMessageW` 让开始按钮在自己的线程上清理状态，`WindhawkUtils::RemoveWindowSubclassFromAnyThread` 同样是一次同步 `SendMessage`。如果任务栏 UI 线程此时完全不处理消息，启动台线程会停在这两个调用上，`Wh_ModUninit` 的 join 也随之等待。

评估：这是「任务栏线程已经卡死」的同一个前提，任何需要跨线程同步的模组都无法避免；Windhawk 的移除子类化接口本身没有超时版本可用。本模组能做的只是保证自己不制造这种阻塞（没有反向等待、没有持锁调用）。不改，归入「任务栏卡死」这一类外部前提。

### 6.6 尚未进行的实机验证

- Explorer 退出（注销/重启）时设置窗口仍打开：`no_destroy` 的实际效果；
- 任务栏分发器在卸载瞬间的排空时间，以及 5 s 兜底是否被触发；
- 锁屏/休眠/重启时电源线程的 join；
- 设备丢失（切换显卡、驱动重启）后的重建；
- StartAllBack / ExplorerPatcher 下的 Win32 与 XAML 开始按钮路径；
- 多显示器、混合刷新率下的打开/关闭动画；
- 真实网页图标的网络与证书错误路径。

以上均无法用离屏测试替代，**不得视为已验证**。

| --- | --- | --- |
| 分组标题后出现「· N 个暂不可用」，且无法去掉 | 标题在绘制时把 `Folder::unavailable`（布局里未能解析的旧目标）拼成了计数后缀 | 删除该后缀；未解析目标仍原样保存在布局文件中，换回原机或重装应用后可自动恢复，但启动器不再显示任何「不可用」字样 |
| 多选图标后不能直接删除 | 批量工具栏只有「取消 / 已选 / 打开」 | 增加「删除」槽位（`取消 / N 个 · 删除 / 打开 N 个`），一次保存批量移除；`VK_DELETE` 在有选中且搜索框为空时同样生效 |
| 「未分组」分组一直显示且删不掉 | 它是未分组应用的容器（inbox）；删除它时 `InboxGroup()` 立刻重建并把应用塞回原处 | 普通视图中不再绘制 inbox 的标题（仅分组编辑模式显示，便于拖动）；删除 inbox 时改为按「从启动器中移除」隐藏其应用，不再重建 |

补充约定：

- 真正的分组被删除时仍把应用交给未分组容器（应用不会丢）；空分组直接消失。
- 多选删除与单个「从启动器中移除」走同一套隐藏集合，可用「恢复已移除的应用」找回。
- `VK_DELETE` 不会抢占文本编辑：搜索框有内容或打开文件夹时，Delete 仍编辑文本。
